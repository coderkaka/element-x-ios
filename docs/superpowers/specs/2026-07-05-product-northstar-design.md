## 1. 愿景与定位

把定制版 Element X 从"聊天客户端 + agent 消息"演进为**通用的目标/进度管理平台**:

- 创业者:管理创业 idea 与推进进度
- 学生:提分计划与执行追踪
- 通用抽象:**项目(目标)/ 任务 / 进度**,不做场景特化的数据模型;场景差异只体现在展示层(远期可做场景预设命名)

**核心分工:聊天 = 控制层,结构化视图 = 观察层。** Agent 在对话流里接受指令、请求决策;任务/进度以 state event 沉淀,由面板和聚合视图呈现。

## 2. 领域模型 ↔ Matrix 映射(已确认)

| 产品概念 | Matrix 载体 | 备注 |
|---|---|---|
| 分组(领域) | Space | 顶层组织,低频切换的范围 |
| 项目(目标) | Room | 一项目一房间 |
| 任务 | `io.element.agent.canvas.steps` state event(key=task_id) | 已实现 |
| 任务的执行记录 | Thread(与任务一对一绑定,`thread_root_id`) | Phase B |
| 决策点 | `io.element.agent.choice_request` 消息 + 同名 state event | 已实现 |
| 项目元数据 | `io.element.agent.goal` state event(key="") | Phase C |
| 主对话流 | 房间时间线 | 项目的总控制台 |

多任务并行是常态:一个项目(房间)内多个任务各绑一个 thread。任何"单任务假设"的 UI(如现 banner)都是过渡形态。

## 3. 命名体系:御案体(已确认)

与 homelab 司署体系(经略司/御史台/将作监/集贤院……)同一世界观:**agents 是百司,用户是君上,本 app 是御案**。

| 概念 | 命名 | 动词/状态配套 |
|---|---|---|
| 分组(Space) | **道** | —(贞观十道,一道一领域) |
| 项目(Room) | **案** | **立案 → 在办 → 结案** |
| 任务 | **差事** | 待办 / 在办 / 已结 |
| 任务的 thread | **实录** | "查看实录" |
| 待决策(choice) | **请旨** | 待批 → **朱批**(用户决策动作) |
| DM/非项目房间 | **书信** | — |

原则:核心名词全上,状态词保持双关可读(在办/已结皆现代通语),不用生僻字;英文侧保持功能性(Projects/Tasks/Messages/Search),不直译梗。

**落地节奏**:Phase B 新建的界面(chip/面板/详情)直接使用御案体文案;既有 tab 改名在 Phase C 统一落地。

## 4. 信息架构(已确认)

### 4.1 底部四 tab

```
[政事]   [差事]   [书信]   [检索]
Projects  Tasks  Messages  Search
```

- **政事**:诸案总览(改造自现 Chats tab),回答"我该看哪个案"
- **差事**:跨案差事聚合(已上线 V1),回答"我该干哪件事";终局演化为看板
- **书信**:DM 与非项目房间。项目房间与普通房间靠 `io.element.agent.goal` state event 区分
- **检索**:保留现状

### 4.2 道(原 Spaces):顶部切换器,不占 tab

- 政事 tab 顶部显示"当前道名 ▾",点开面板:道列表(切换范围)+ "管理"入口
- 切换道后,案列表与差事看板都过滤到该道(经用户确认:多上下文隔离是真实需求,保留此层)
- 现有 Space 管理界面全部保留,仅迁移入口
- 参照 Slack:workspace 切换在 iOS 是左缘抽屉(近零可见性);我们改用顶部显式入口换可发现性

### 4.3 政事 tab(Home)内容结构

```
┌ 当前道名 ▾
├ 【请旨待批】横条(有 pending 决策才显示)→ 跨案 choice_request 聚合
├ 案卡片列表:案名 | 差事进度(5/8)| 最近动态一行 | 未读・待批红点
├ 排序:有待批 → 有在办差事 → 最近活动
└ 空态:「暂无立案」,引导立案
```

## 5. 房间(案)内层次(已确认,Phase B 主战场)

```
案(房间)
├ 顶部进度 chip:「3 件差事在办 · 1 件请旨待批」(替代现单任务 banner)
│   └ 点击 → 案卷(房间任务面板)
│       ├ 【待批】区:本案 pending 的请旨(点击滚动到卡片)
│       ├ 【在办】差事列表:标题 | 步骤进度 | 点击 → 差事详情
│       ├ 【已结】折叠区
│       └ 差事详情:步骤列表(已实时更新)+ 「查看实录」 → 跳转绑定 thread
└ 时间线:主对话流(卡片仍在此出现,作为事件流的一部分)
```

### Phase B 五个落地决策(推荐方案,已随本文档确认)

1. **banner 处置**:直接替换为多任务进度 chip(单任务时显示任务名,多任务显示计数)
2. **面板形态**:push 页,与现有 `CanvasStepsScreen`(任务详情)构成两级导航,复用现导航栈
3. **thread 绑定 V1**:单向——任务详情里"查看讨论"跳转 thread;thread 内显示任务状态条留到后续
4. **待决策进面板**:进,作为面板顶部独立区(数据自 `fetchedStateEvents`,现成)
5. **已完成任务**:面板内折叠区展示,不设时限;"N 天后隐藏"的归档策略留给 Phase D 数据量大了再说

## 7. 产出物架构(过程/产出/索引三分)

```
案卷(索引层)—— 这个案有什么
├─ 差事:进度、metric 进度条(如 118/130 分)
│   ├─ 实录(thread)→ 过程:讨论、推理、波折
│   └─ 附卷 → 产出:报告/方案/图表/代码/网页
└─ 结案陈词(result)
```

**核心原则:产出物的存储与展示解耦。**

- 存储:附卷即时间线里的一条消息(markdown/图片/文件),差事以 `artifact_event_id` 引用;
  或以 `artifact_url` 指向一个网页(见下)。
- 展示:案卷中点附卷打开**全屏查看器**渲染内容,而非滚回聊天气泡。查看器按内容类型
  逐步升级(markdown 渲染、diff 查看器…),不动存储架构。
- 版本:文档修订=发新消息,state 重指 `artifact_event_id`;旧版本自然留在时间线,免费的版本历史。
- 量化趋势:Matrix 保留 state event 历史,metric 时间序列直接读 state 历史,零新增存储。
- **网页附卷(`artifact_url`)**:应用内 WebView/SFSafariViewController 打开任意网页;agent 可在
  homelab 生成 HTML 报告供全屏渲染,表现力无上限。边界:webview 内容不在 Matrix 加密/审计
  范围内,适合展示、不作为事实源。
- 诚实的天花板:实时协同编辑(Google Docs 式)不适合 Matrix 承载,该场景以 `artifact_url` 跳出。

### 差事 schema 演进(全部可选字段,向后兼容)

| 字段 | 层级 | 用途 |
|---|---|---|
| `description` | 任务 | 背景/目标一句话 |
| `metric` `{current,target,unit}` | 任务 | 量化进度(学生场景命门) |
| `result` | 任务 | 结案陈词 |
| `note` | 步骤 | 单步结果备注 |
| `artifact_event_id` / `artifact_url` | 步骤 | 附卷引用(Matrix 事件 / 网页) |

已定稿部分见 `~/homelab/element-agent-protocol.md`(hermes 适配规范)。演进字段:

| 字段/事件 | 阶段 | 用途 |

## 9. Slack 参照系(结论)

**采纳**:Home/DMs 分离;workspace 不占 tab;Canvas-per-channel(=房间任务面板);Slack Lists 的"条目↔thread"交互(=任务详情跳 thread);Activity 概念改造为"需要你(待决策)"聚合。
**不采纳**:把 Lists/Canvas 埋进 Files 二级入口(Slack 里任务是附属,我们这里任务是主产品,必须一等 tab);More tab 式的功能堆叠。
