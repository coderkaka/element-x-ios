## 设计原则:什么时候该走 agent 对话,什么时候该走直接 UI(07-06 讨论)

不是"能力时代到了就该都用自然语言"。判断标准是**这个动作有没有真实的复杂度/歧义/风险
值得委托给一个聪明的中间人**:

- **值得委托**(→ agent 对话 + 审批卡,如 D-7 运维常设房间、案/道创建):有协议复杂度(权限/
  goal state 这类多步且容易漏)、有真实判断(叫什么名字、归哪个道)、有执行风险(错了
  代价高,如 PL0 事故)。
- **不值得委托**(→ 直接 UI,如"+开始聊天"、设置里的开关):零歧义、零风险、纯机械
  (你已经精确知道要什么)。自然语言不是免费的——一次推理往返的延迟、理解错的风险、
  "要记住该怎么说"的认知负担,这些成本只有在任务真的需要委托时才划得来。把"跟 Alice
  开始聊天"这种动作硬塞进对话流程,只会更慢、更不可靠,不会更"未来"。
- 中间地带(如批量/条件性设置:"把除运维常设房间外所有房间都调成免打扰")值得留意,但现在
  不用为此改任何东西,真出现这类需求再考虑。

## D-1 差事看板(差事 tab 终局)

- 列表 → 看板:按案分列 ↔ 按状态分列(待办/在办/已结)可切换。
- 条目点击 → 直达对应房间的差事详情(`CanvasStepsScreen`),而非只进房间
  ——数据已具备(index 携带 roomID + taskID;详情页已支持 taskID 驱动的实时刷新),
  缺的是 RoomFlowCoordinator 的"跨 tab 深链到详情"路由。
- 依赖 C:无硬依赖;依赖 hermes 按 B' 协议写 state(否则看板数据不完整)。
- C 期间不堵死:差事 tab 保持独立 screen,不与政事耦合。已满足。

## D-3 归档策略

- 触发:已结差事数量大(案卷折叠区变长)、结案的案挤占政事列表。
- 机制:goal `status: "archived"`(已解析,C-2 落地)→ 政事列表隐藏 + 检索可达;
  差事级别沿用 state event 的 `status: "done"` + 面板折叠,超阈值(如 30 天)客户端本地
  截断显示(state 历史仍在 Matrix,永不丢数据)。
- 决策留待有数据时:阈值、是否需要"归档"显式动作、结案的案是否自动 leave room。

## D-6 标的(objective)—— 案内阶段目标,AgentOS 已开始服务端预写

- 协议(`~/homelab/docs/element-agent-protocol.md` §3.4,版本 2026-07-06c):新增
  `io.element.agent.objective`,state key = `objective_id`,**案内多实例**,粒度介于
  `goal`(单例/长期/案为什么存在)和 `canvas.steps`/`choice_request`(执行级)之间——
  回答"这个案当前在验证/达成什么阶段目标"。`success_metrics`/`exit_options` 是标的级
  质性判断字段,不等同于差事级 `metric{current,target,unit}`(前者回答阶段何时算完,
  后者回答量化进度)。
- 关联方向跟 `canvas.steps`/`choice_request` 一致:**子级(差事/请旨)带可选
  `objective_id` 指认父级**,标的本身不维护子级列表——同一套"客户端查询时 join、
  避免双写竞态"模式,零新设计成本。
- **SDK 侧已完成**(07-06 本地会话):`io.element.agent.objective` 加入
  `AGENT_EXTRA_REQUIRED_STATE`(`matrix-sdk-ui/src/room_list_service/mod.rs`),
  fork 已重编。数据现在能进本地 store 了,但 **Swift 侧解析/索引/渲染仍留 Phase D**——
  跟 `metric`/`needs_user`/`scenario` 同一套"协议先落地,客户端不消费"policy,不因为
  hermes 已经在写就提前实现。
- **呈现方向已定(07-06 讨论,写入设计但不实现)**:
  - 案卷面板(房间内):按 `objective_id` 分组差事/请旨,标的作为可折叠 section,
    `success_metrics` 展示为只读清单(不做可勾选组件,标的完成与否权威来源是
    `status` 字段);`exit_options` 也只读展示,真正的阶段决策仍走已有的
    `choice_request` 卡片,不为标的单独发明新交互组件。
  - 政事堂案卡片(跨房间列表)—— **07-06 修正:不挑单一标的做标题**。原方案是取
    `priority` 最高的 `active` 标的标题当副标题,但 `priority` 的方向连协议文档自己
    都没写清楚(见下),挑出来的"代表"本质是随机的,会给用户一个"这案子现在只干这一件
    事"的假单线叙事。改成按数量分两种情况诚实呈现:
    - 恰好 1 个 `active` 标的 → 直接显示它的标题(无歧义,该显示)
    - ≥2 个 `active` 标的 → 不挑标题,只显示中性提示,如「2 个标的并行推进」,具体是
      哪两个留给点进案卷面板看分组明细
    - 没有任何 `active` 标的(旧协议房间/尚未立标的)→ 卡片退回现状,只显示差事 x/y
  - `priority` 已与 hermes/AgentOS 对齐为**数字越大优先级越高**,但它只适合作为同状态
    标的的人工排序提示,不是状态机字段。**建议**:凡是能用 `updated_at`(时间戳,方向天然
    无歧义)替代的排序场景(如案卷面板内标的 section 顺序,取"最近有动静的排前面"),
    优先用 `updated_at` 不用 `priority`,减少人为权重带来的解释成本。
- **07-07 更新**:D-5 的合并已完成——`AgentTaskIndexService`/`AgentProjectIndexService`
  合并为 `AgentIndexService`,标的索引可以作为第四个 publisher 加在上面,不再是"先加
  第三份重复实现"的问题。**但 D-6 仍不建议现在做**:跟 D-2②的 metric 字段同理,
  `io.element.agent.objective` 目前没有任何 agent 在真的写(查过 homelab,一个引用都
  没有),建出消费管线也只是空索引。等真实数据出现再做。

## D-7 系统运维常设房间——统一入口(现有道 + 多 agent 房间,不是新屏幕、不归书信)

07-06 讨论:能不能让空间/房间运维(建道/建案/权限/邀请)全自动化,用户只说意图,底层
直接操作。结论是可行,而且这套系统已经有现成架构承接——`~/homelab/docs/
AgentOS统一审批设计.md` 的 approval registry + `agent-os.matrix-gateway` +
`choice_request` 展示,核心闭环已落地,建道/建案只是给它加一个新 `kind`,不是新基建。

**排除的两个方向:**
- **不给 ElementX 自带一个运维 agent**:协议文档把 client 定死为"展示协议,不是审批
  事实源"。客户端自己再实现一套能操作 Matrix 的 agent,等于让同一件事有两个执行者,
  正是审批设计文档"关键风险"里点名的"双事实源"。运维能力应该始终留在 agent-os(常驻
  服务端),client 只需要能方便地"跟它说话"。
- **不归书信 tab**:书信=私人通信(DM),给事中/运维常设房间是系统的正式中枢通道,语义上跟
  "私人书信"不是一类东西,硬塞进去会让书信 tab 的分类变脏。

**落地方向:不默认新建系统道。** 当前 homelab 已有 `枢密院` 承载 Hermes/Hermes Alert
等运维相关房间;系统运维入口应优先表现为 `枢密院` 下的一个多 agent 常设房间/衙署,
运维意图在这个房间发起。只有未来运维域膨胀到需要独立顶层空间时,才考虑把它拆成
单独的道。

- **角色澄清(07-06 用户纠正)**:给事中不是运维负责人,协议原文写得很清楚——「给事中
  只做收发/兜底聚合,不是所有审批的默认出口」。真正的权威执行方是 **@agent-os**(协议
  称"中枢控制账号")——不管房间里哪个 agent 身份在说话,`choice_request` 的
  pending/resolved 状态事件始终由它一个账号写,这是唯一事实源。各司账号(将作监/御史台
  等,如果各自有独立 Matrix 身份)按职能在房间里发言、发审批卡,但不写状态。给事中可以
  是房间里的一个成员,负责它文档定义好的那个窄职能(兜底转呈),不是唯一的脸。
- **为什么这个设计比"归书信"或"自建 agent"都优雅**:
  - 复用道/房间机制,零新 UI——道条(`SpaceTabBarView`)已经把所有道列成 filter chip,
    常设运维房间只是现有 `枢密院` 下的一间普通房间,不需要新屏幕/新按钮/第五个 tab。
  - 多 agent 参与的房间天然不是 `m.direct`(1:1 DM 才会被打这个标),不会被政事 tab
    "排除 DM"那条规则误伤扫进书信——这条之前顾虑的技术前提在这个方案下自动满足。
  - 多发送者在同一房间说话,是通用 Matrix 客户端本来就支持的能力(发送者身份来自
    event 的 `sender`,各自按自己的头像/显示名渲染),不需要客户端改一行代码。
- **建房间时的权限清单**(跟建案/建道同一类必修项,写给 homelab/agent-os 侧执行):
  君上(用户)PL100;@agent-os PL50 起(唯一写状态的账号,需要够写自定义 state event
  的权限);其他各司账号默认 PL 即可,不需要单独提权,因为它们只发消息不写状态。
- **安全边界重申,不因为这个设计而松动**:运维常设房间是"发起/讨论运维意图"的地方,不是
  "可以绕过审批"的地方。审批设计文档"非目标"第一条("不让任何 agent 自动替人批准高风险
  动作")在这里同样适用——执行链路不变:意图 → 审批卡(`choice_request`)→ 用户点选 →
  执行。
- **已知的小尺寸问题,不急着解决**:这类常设房间没有 `goal` state(它不是"案"),挂进
  政事道条筛选后会渲染成普通房间行,不是案卡片(没有差事进度/待批红标那些视觉),跟同一
  列表里的其他案卡片风格不统一。现有渲染逻辑对无 goal 的房间本来就会优雅退化,不会报错
  或难看,先不管,真用起来觉得别扭再调。
- **对 element-x-ios 的结论:客户端侧零代码改动。** 落地工作全部在 homelab/agent-os:
  在现有合适的道下建多 agent 常设房间、邀请该邀的 agent 账号、按上面清单设权限、把这个
  room 标记正确(不能是 `m.direct`)。
- **连带确认**:D-6/D-4 附近提过的"+ 号菜单加建道入口"进一步确认**不需要做**——建道/
  建案走"跟运维常设房间里的 agent 说意图 + 审批卡确认"这条路,不需要客户端一套独立的手动创建
  表单(独立表单本身是 bug 磁石,容易漏设权限/漏写 goal,跟历史上那次 PL0 事故是同一类
  风险)。

## D-8 四 tab IA 复核(07-06 讨论,均未实施)

**入口分布现状(已核实)**:Settings(政事顶部头像)和"+开始聊天"目前**只存在于政事
tab 自己的工具栏里**,差事/书信/检索三个 screen 一件工具栏 item 都没挂。upstream
原版的先例是 Chats 和 Spaces 两个页面各自维护一份 Settings 按钮,不是共享一层壳——
照这个先例,后续要做的是**在差事/书信(未来检索重启也算)各自的工具栏里加同一份
Settings 入口**,不是架构性地做共享 chrome 层。工作量:每个 screen 照抄现成的
action 接线(Model/ViewModel/Coordinator 各加一小段),机械但不难。

**全局"+"保留,范围收窄确认**:D-7 那条"案/道创建走 agent 对话"的原则**只管案和道**
——因为只有它们有协议复杂度(权限/goal state)。开始跟一个已知的人聊天、按地址加入
房间、浏览公共目录,跟 agent-os 无关,是最基础的 Matrix 客户端功能,继续走直接 UI。
延伸事实:Matrix/Element X **没有独立于房间之外的"好友"概念**——`StartChatScreen`
选中一个人就直接 `createDirectRoom`,"找人"和"加好友"本来就是同一个动作,没有额外
一层"好友关系"复杂度,所以也没有额外理由把它塞进对话流程。

**道条形态复核,维持现状**:横向可滑动的头像+名字药丸条(现有形态)在头对头比较
下确认保留,没有改成下拉切换器(北极星文档最早方案 §4.2)或纯图标条的必要。
**唯一确认要升级的交互**:重排从"长按弹 context menu 点左移/右移"换成**真正的
按住拖拽**——更符合 iOS 用户对"整理图标"式重排的直觉。工作量提示:道条是手搭的
`ScrollView`+`HStack`,不是原生 `List`,真拖拽要自己接手势+位置计算+动画,是中等
工作量的打磨项,不是加个 modifier 就完事。

**道下常设房间(暂定名衙门/衙署,或角色化叫道台)**:"就是想聊聊,不代表要立案"这
个需求不需要新机制——直接在房间里说话,跟差事/请旨卡片共存无碍(D-7 运维常设房间已经是
这个模式的系统级实例)。这里把它推广到**每个道都可以有一个没有 `goal` state 的
常设房间**,里面是该领域相关的 agent,区别于真正有目标、会推进、会结案的案。
- **技术区分免费**:有没有 `io.element.agent.goal` 就是有没有案,`AgentProjectIndexService`/
  `HomeScreenRoom.isProject` 现在就是这么判断的,不需要新代码。
- **叫法候选**(命名权在用户):衙门/衙署(房间本身,常设办事处)、道台(拟人化这个
  领域的 agent 角色,呼应给事中/御史台/将作监这类系统级角色命名)。
- **一个未定的小 UI 想法**:选中某道后,这个常设房间排在该道房间列表最前面(先到
  衙门,再看具体案),不算现在要做的事。

**书信 tab 复核 —— 标记为下一轮 IA 简化头号候选,不现在动**:
- 这个产品的重心是"人跟一群 agent 协作",不是"人跟人社交"——私聊在这里本来就是
  边缘场景。上面两条(无好友概念、讨论走道下常设房间不需要私聊)进一步削弱了书信
  独立存在的理由。
- **已核实 `MessagesScreen.swift` 目前零自定义功能**——没有任何工具栏 item,纯粹是
  `messagesRoomSummaryProvider` 过滤出的 DM 列表,点开就完了。等于是个白板,后续
  替换/移除的切换成本几乎是零,不是要拆什么已经嵌入很深的东西。
- **结论,不现在执行**:不因为今天的推理就直接砍(书信/C-1 是真做过、真验收过的
  东西),但明确标记它是下一轮 IA 简化的头号候选——用一段时间之后回头看,如果书信
  tab 真的一直空着,收成三 tab(政事/差事/[检索]),腾出来的位置留给"需要你"聚合
